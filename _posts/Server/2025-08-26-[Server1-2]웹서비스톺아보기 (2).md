### 3. WAS의 등장 (단방향 통신에서 양방향 통신으로)

꾸밈과 동작이 추가되고 이용자가 많아지면서, 서버는 단순히 문서를 송수신하는 역할을 넘어 서비스 로직을 수행해야 했다.
이때 등장한 것이 WAS(Web Application Server)이며, 여기서부터 웹은 정적 문서가 아니라 동적 서비스 플랫폼으로 발전했다.

백엔드에서 가장 핵심적으로 다루는 로직은 크게 두 가지다.

1. 로그인/인증

사용자가 누구인지 확인하고, 그 상태를 유지하는 과정이다.

대표 방식: 세션(Session, Redis 저장)(세션), JWT(Json Web Token) 기반 토큰(유저를 구분하지 못함)
=> 쿠키를 이용해 이를 가능하게 함

여기서 앱과 웹의 차이도 발생한다.
- 웹: 브라우저-서버 간 쿠키/세션 관리 (OAuth, JWT도 사용하기 때문)
- 앱: 토큰 기반 인증을 선호 (예: OAuth, JWT), 서버 부하를 줄이고 클라이언트 단의 상태 관리 강화

2. API (CRUD)

WAS는 단순 문서 저장소가 아니라, 클라이언트의 요청에 맞춰 데이터를 Create, Read, Update, Delete 할 수 있는 인터페이스를 제공한다.

예: 게시판 글 등록/조회, 쇼핑몰 상품 목록 가져오기, 결제 요청 처리 등

즉, WAS의 등장은 웹이 “단방향 문서 전달”을 넘어서 “로그인/인증을 통한 상태 관리”와 “API를 통한 데이터 가공·제공”을 가능하게 했다는 점에서 중요한 전환점이었다.

### 5. 현대의 백엔드 개발자가 봐야할 곳
서버를 3계층으로 본다면 i) Web server, ii) WAS, iii) DB server로 볼 수 있다.

각각의 계층에서 백엔드 개발자는 성능최적화를 시행해야하고 다음과 같이 볼 수 있다.
i) Web server
송수신 서버는 네트워크의 문제다. 우리나라와 같이 좁은 경우, 이에 대해 문제가 생길 일이 많지 않다.

ii) WAS
WAS는 요청을 주고 받고 이에 대한 서비스 로직을 실행하는 곳이다.
네이버 홈페이지를 만들기 위해서도 몇백개의 요청이 만들어지고 이에 더해, 인터넷사용자도 많아지기도 했으며, 나아가 요즘 사용하고 있는 인공지능 서버의 경우에는 client의 한번 요청에도 안에서 많은 요청을 다루기 때문에 이 대규모 트래픽 요청에 대해서 어떻게 처리할지가 가장 많은 관심사다.

![토스채용조건](/assets/images/0826/traffic.png)

APM과 같은 대시보드 시각화 오픈소스와 더불어 위와 같은 프로메테우스와 그라파나와 같은 툴로 잘 모니터링을 하는 것이 중요해진 이유기도 하다.

Spring을 쓰면 JAVA의 인스턴스관리도 된다는데 이것은 나중에 또 톺아보겠다. 


iii) DB server
그리고 WAS의 성능에는 해당 데이터를 잘 가공하고 서비스로직을 빠르게 처리하는데도 있지만 그 데이터를 어떻게 잘 탐색하고 가져올 것인가에 대해서도 중요하다. DB스키마를 어떻게 효율적으로 잘 짜고, WHERE조건을 잘 다루는 것은 물론, 도메인 내에서도 필요한 우선순위가 다르기 때문이다.

주어들은 바로는 Buzzwords의 Garbage reasoning 작업이라고 한다. 이를 어떻게 하냐에 따라 필요한 정보를 잘 얻을 수도 있는거고 우리가 관리하는, 잘 정리된 DB서버더라도 스키마 및 탐색을 어떻게 설정할 것인가에 따라 DB접근 속도가 달라진다고 한다.
